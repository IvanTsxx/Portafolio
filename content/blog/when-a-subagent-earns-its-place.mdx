A subagent is a fresh agent with its own context window. It receives a brief, does the work and returns a summary. The main thread never sees the files it read or the commands it ran. That is the benefit and the cost.

## The test

I delegate when three things are true.

1. The work is independent. It does not need what the main thread learned in the last hour.
2. The result is checkable. It is a diff, a list of findings or a command that passes.
3. The detail is disposable. I want the conclusion, not the forty files that produced it.

If one of them fails, I do the work in the main thread.

## What I delegate and what I keep

| Task | Delegate | Why |
| --- | --- | --- |
| Find every use of an API across the repo | Yes | The output is large and the answer is short |
| Audit components for missing states | Yes | Independent work that returns a list |
| Rename a prop used in thirty files | Yes, to one agent | Mechanical and verified by the typechecker |
| Design a data model | No | It needs the full context and a judgment call |
| Fix a bug I cannot explain yet | Not yet | The investigation is the work |
| Two agents editing the same file | No | Shared writes have to be serialized |

## Write the brief like a handoff

The subagent starts with nothing. Whatever is not in the brief does not exist for it. A good brief fits on one screen.

```txt title="brief.txt"
Goal
Add an empty state to the work archive when a filter matches nothing.

Scope
components/content/work-archive.tsx only.

Constraints
Use the existing tokens. No new dependencies. No code comments.

Done when
Typecheck and lint pass, and the empty state renders with the filter applied.

Report
List the files changed and anything you could not verify.
```

Pointing at files beats pasting their contents. The agent reads the current version instead of a stale copy.

## You still own the result

<Callout tone="tip" title="Read the diff, not the summary">
  A summary describes what the agent meant to do. The diff shows what it did.
  When they disagree, trust the diff and run the checks yourself.
</Callout>

An agent that writes files gets its own worktree, so its edits cannot land in a lane that someone else is using. I review that diff the same way I review a colleague's pull request.

## When it costs more than it saves

Every subagent needs a brief, an isolated place to write and a review pass. For a three-line change that overhead is larger than the work. I make the edit myself.

The same goes for tightly coupled changes. If step two depends on a decision made in step one, splitting them across agents only moves the coordination cost somewhere harder to see.
