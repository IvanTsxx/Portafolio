A skill teaches an agent how to do something. An MCP server gives it something to do it with. They answer different questions.

## Skills carry procedure and taste

A skill is a folder with a `SKILL.md`. The agent reads the description up front and loads the rest only when the task matches. It costs tokens only when it loads.

```md title=".claude/skills/ui-states/SKILL.md"
---
name: ui-states
description: Trigger when writing or reviewing UI code. Apply the states and accessibility checklist.
---

# UI states

1. List the states before writing code.
2. Resolve combinations: disabled, loading, focus, selected, hover.
3. Make states explicit with data attributes.
```

## MCP servers carry access

A server exposes tools and resources over a standard interface. Design tools, issue trackers and content systems are typical. Its tool definitions sit in context, and it needs credentials.

```json title=".mcp.json"
{
  "mcpServers": {
    "docs": {
      "type": "http",
      "url": "https://example.com/mcp"
    }
  }
}
```

## How I decide

| Question | Reach for |
| --- | --- |
| The agent keeps making the same mistake | A skill |
| The information lives in another system | An MCP server |
| The task needs a procedure or a point of view | A skill |
| The task needs to read or write somewhere else | An MCP server |
| The task needs both | A skill that names the MCP tools to call |

<Callout tone="tip" title="Rule of thumb">
  Write a skill the second time you correct the same mistake.
</Callout>

## Using them together

A design-to-code skill can say: read the frame with the design tool, map values to the repository tokens, then verify. The skill carries the judgment. The server carries the access.

## What I keep connected

Only the servers a task needs. Fewer tools in context means fewer wrong turns.
